# Generation foundation

This explanation covers the default numerical `planned-v1` route, as inspected September 22, 2026. [API](API.md) owns operation contracts; [NEXT-EXPERIMENT.md](NEXT-EXPERIMENT.md) owns pending work. Qualitative concept rules differ from the numerical policy below.

Generate a recognizable character whose upgrades give a player understandable purchasing choices. Keep model work bounded and inexpensive. The [supplied research](../research/game-design/README.md) informs this foundation: start with the intended decision, specify observable changes and limits, then test the claim. It does not establish BTD6 facts or authorize new Engine behavior.

The design contract is: in this situation, buy this path because it changes this behavior, at this cost, while retaining this weakness. Compiled effects show what changed. Evidence distinguishes a design intention from an observed result.

The [PR comparison](PIPELINE-APPROACHES.md) records which ideas from PR5 through PR8 and the separate anime-to-BTD6 pitch were retained or rejected. The [character design guidance](../research/game-design/CHARACTER-DESIGN-GUIDANCE.md) informs qualitative planning: actual motions and triggers, varied progression, explicit hit capacity and inheritance, six crosspaths and cheap-copy checks. It does not authorize unsupported mechanics or replace the numerical stage required by `planned-v1`. Qualitative concept authoring is a separate supported Deliverable; see [current next work](NEXT-EXPERIMENT.md).

For example, a precision branch may promise sustained pressure on separated durable enemies. More damage and personal detection can support that adaptation. Calling it an armor-piercing beam cannot grant an undeclared immunity bypass. Its capstone must explain the value of concentrating investment compared with cheaper copies, retaining placement and target-access assumptions.

## Default numerical pipeline responsibilities

`Evidence + explicit Request → purchase plan → numerical mechanics → compile and check → purchase evidence + Unit`

The default remains `planned-v1`: two normal model calls, each with at most one correction by default. Provider failures are not design-repair opportunities. There is no automatic paid fallback and no required model critic, Jev ranking or image generation. CLI and Lab share the same core. Revisions use the same process and retain confirmed choices.

| Owner | Responsibility |
| --- | --- |
| Request and evidence | Character identity, continuity, rules, constraints, references and gaps. A citation identifies supplied text; it does not establish source truth or ownership of every mentioned power. |
| Model purchase plan | Recognizable concept and signature, relevant repertoire, base action, three purchase situations, weaknesses, capstone value and each milestone's promised change. |
| Model mechanics pass | Propose supported effects and incremental prices implementing those promises. The model still selects numbers; there is no automatic balancing solver. |
| Engine | Legal build structure, citation joins, code-owned labels, budgets, arithmetic, integer counts, scoped effects, compiled descriptions and analytical comparisons. |
| Human or optional model review | Source interpretation, meaningful alternatives, prose fidelity and purchasing reasons. These judgments do not certify balance. |
| Consuming game and Towerright | Runtime, maps, waves, roster-wide T5 ownership, wider balance, observed player behavior, project history and Acceptance. |

`purchase-plan-v1` is the compact provider contract within the existing route. Each milestone pairs `change`, `improves` and `unlock`. Code expands it into compatible `run.designPlan` data. The model does not author a second intent tree or six crosspath explanations. Early crosspath summaries come from T1/T2 intentions; actual effects are measured after compilation. The mechanics response omits plan-owned names, themes and citations, which code binds before strict decoding.

Citation capacity follows the bounded 96-passage authoring catalogue, replacing the former two-citation section limit and eight-fact total. Exact duplicate IDs join once; distinct supporting passages are not truncated. Every ID still has to resolve to supplied evidence. The planner's allowed unlock and improvement enums exclude known forbidden tier/path choices, while local validation independently enforces them.

Planning rejects provably impossible commitments before the numerical call: unavailable extensions, prohibited early transformations, missing same-path boosts and minimum effect counts exceeding the Definition. Resolved checks compare every purchase against its predecessor in every legal build. Passing preflight does not guarantee compilation. Unexpressible powers remain omissions or unapproved mechanic proposals.

## BTD6 default and reusable references

The executable Definition and [default Profile](../src/core/default-profile.ts) own rules. [Mechanics](MECHANICS.md) explains supported operations. [BTD6 research](../research/btd6/PATTERNS.md) and [worked progressions](../research/btd6/BTD6-UNIT-EXAMPLES.md) explain patterns and source limitations.

- T1/T2 improve the general basic attack and remain useful as crosspaths.
- T3 commits to a narrower job, often changing attack behavior. T4 develops it; T5 is its ultimate version.
- Buy at most two paths. Only one exceeds T2. After `3-0-0`, `3-1-0` and `3-2-0` remain legal; `3-3-0` and `3-2-1` do not.
- Broad role labels may repeat when purchasing reasons differ. Identical T1 behavior remains forbidden by the default policy.
- Capstone value has no universal multiplier or mandatory new-effect quota. Numerical development can be appropriate; a dramatic name or larger price is not evidence of value.
- Gold is the currency. Health is the shared life pool, not Unit durability. The consuming game must enforce one placed T5 per player, Unit type and path; this generator does not enforce roster-wide placement.

These are deliberate numerical BTD6-inspired defaults. Some original towers introduce early secondary systems that this numerical Profile excludes; concept rules allow bounded early auxiliary behavior. Other games can contribute small, attributed examples of situations, progression, costs, weaknesses and interactions. Keep versions and missing values visible. Reuse principles where the supplied Definition supports them. A reference pack is evidence, not a plugin or permission to import mechanics.

The report's art, audio, motivation and playtesting sections guide consumer design. This foundation does not specify runtime, animation, telemetry or UI implementations. Typed effects provide feedback in the sheet; a consumer still needs to test player understanding in play.

## Evidence and iteration

Numerical typed drafts retain `run.designEvaluation`, computed without a model call. It separates source and purchase claims from T2→T3, T3→T4 and T4→T5 deltas, legal secondary T1/T2 contributions at each advanced tier, and T4 copies affordable at the T5 budget. All six directional crosspaths are covered, including later changes to active output. `render --details` exposes comparisons; the ordinary sheet stays focused on the kit. Rechecking detects evidence edited out of agreement with the blueprint.

Direct damage assumes continuous access to an eligible durable target. Group and control values are capacity upper bounds. Active peaks are not sustained output. Extra copies need extra space and target access; range and duty fraction do not add across copies. Nonfinite estimates are unavailable, not zero. These comparisons cannot establish actual crowd density, geometry, immunity outcomes, economy, canon relevance or enjoyable play.

Evaluate against the same frozen corpus. Generate the batch sequentially, then review outputs together. Record completion without repair, completion after repair, failures, latency, tokens, reported cost and unknown charges. Inspect recognizable identity, unsupported promises, branch alternatives, progression payoff and crosspath value independently of structural success. A useful failure identifies the affected purchase and assumption, not an invented quality score.

Start with the smallest evidence-supported correction to source selection, contract, rule, compiler or reference. Do not compensate for representation failures with a stronger paid model. Add vector storage, agent orchestration, optimization or simulation only when a repeatable failure and bounded comparison justify it. A single-call route remains a possible experiment; the current two-call boundary preserves an independently stated intention before execution.

All three September 21 foundation free-model batches produced zero complete drafts from three characters. The final batch included the grammar fixes and character-design guidance; it still failed numerical validation and independent source/progression review. This foundation supplies construction and inspection boundaries, but it does not yet meet the quality, speed or reliability target. Measurements and remaining failures belong in [pipeline evaluation](PIPELINE-EVALUATION.md).
