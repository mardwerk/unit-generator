# Refining generation with evidence

Concept operations are implemented; repeatable design quality and preservation across real outputs remain to be established. Retain evidence during development, then freeze a repeatable version for a controlled study. This September 22, 2026 priority supersedes numerical-backend extraction or PR 6 evaluator work as prerequisites. Those remain separate work when needed. [NEXT-EXPERIMENT.md](NEXT-EXPERIMENT.md) gives the current acceptance criteria; the [core reshape](GENERATOR-RESHAPE.md) records later portability work.

## Diagnose the earliest evidenced failure

| Failure class | Evidence to inspect | Smallest useful next action |
| --- | --- | --- |
| Identity or source coverage | Resolved subject, source snapshot and actual selected passages | Fix retrieval/selection before comparing models |
| Source interpretation | Relevant passage versus the model's claimed limitation or ownership | Correct scope handling or examples; distinguish deliberate omission from absent evidence |
| Character organization | Grouping rationale, alternative layouts and user preference | Revise the interpretation contract; do not tune damage to repair a weak identity |
| Unsupported behavior | Proposed operation versus implemented capabilities | Revise the adaptation or implement a scoped module; retain the proposal |
| Supported promise implemented incorrectly | Promise, typed intent and before/after resolved effects | Fix contract translation, decoding or generation for that operation |
| Repair regression | Same evidence plus changed fields and lost prior benefits | Narrow repair scope and recheck dependencies, not only the original diagnostic |
| Overrestrictive authoring policy | Failed policy plus a concrete otherwise coherent counterexample | Review that policy independently; never erase runtime invariants to improve pass rate |
| Runtime or strategic failure | Executed scenario, actions, outcomes and policy competence | Change one mechanic/parameter or evaluator defect, then rerun the affected scenarios |
| Readability or preference | Pairwise human reason or player observation | Revise the relevant design choice; record disagreement rather than manufacture an objective score |
| Cost or latency | All attempts, repair calls, timeouts and reported/unknown usage | Remove redundant model work; compare equal total budgets |

The retained [pipeline evaluation](PIPELINE-EVALUATION.md) contains source-reading, intent, implementation and repair failures. Some promised volleys and boosts already have vocabulary. Calling all failures “missing mechanics” would prescribe the wrong fix. Conversely, support for static boosts does not implement shared forms or stamina.

Keep one trace row per consequential finding:

```text
Run and candidate revision | Character/build/purchase | Source passage
Interpretation and selected grouping | Promised behavior | Typed intent, if present
Implemented before repair | Implemented after repair | Final diagnostic
Failure class | Human judgment and reason | Status or unknown
```

Use the existing request/response files and render output. For rejected drafts, label the row unpublished. Do not infer observed gameplay from analytical deltas. The first failure table can be Markdown beside the existing evaluator report; a new dashboard is unnecessary.

## Score dimensions separately and decide

Report complete returned drafts, first-pass validity, repaired validity and failures with denominators. Report source fidelity, organization, branch choice, progression, crosspath contribution, readability and human correction effort with affected decisions and reasons. Report total latency, tokens, calls and known/unknown cost. Runtime performance and preference remain unavailable until tested.

A low-cost failure is still a failure. A legal but generic kit is a structural pass with a quality problem. A thoughtful plan rejected by the compiler is a promising intermediate artifact, not a completed unit. At least one independently reviewed usable result is a useful signal for retaining an optional experiment, not enough to promote a default or claim general superiority.

For each completed batch, record one decision: keep the route for further study, revise one identified failure, or drop it. Preserve the current default unless a matched comparison shows a concrete advantage without losses in source ownership, executable promises or revision behavior. Define acceptable latency and completion targets before a promotion trial; this task supplies no justified universal threshold.

If every route fails, choose the earliest recurring evidenced defect and fix that one. Do not add a stronger model, another critic and relaxed gates simultaneously. After the correction, replay retained responses offline where meaningful. Replay tests code against existing output; only a new generation tests the changed prompt or model.

## Refine a unit at the right level

Feedback should identify whether the user rejects the source scope, character organization, path identity, purchase behavior, numbers or presentation. Preserve explicitly confirmed choices. Reorganizing paths invalidates dependent milestones, crosspath explanations and numerical comparisons. A number-only revision should not reinterpret the character. A wording-only revision must not change behavior.

Carry the selected interpretation's invariants into repairs. Compare changed fields and lost effects against the pre-repair candidate, then rerun affected legal builds and all final publication checks. Do not preserve an unconfirmed assumption just because the previous model proposed it. Existing previous-Result and feedback inputs are useful foundations, but an explicit invariant/impact record is proposed work, not an implemented guarantee.

Retain user preferences with a reason and scope in the caller's project. Private character mappings are not public fixtures or universal recipes. Include original negative examples where borrowed stat packages pass checks but lose identity, and references with no transformations to detect overgeneralization.

## Optimizations in order

First establish preservation across real concept generation, save/reload, revision and presentation. These operations already exist; offline retention does not establish live semantic preservation. Retain exact inputs and attempts from development. Fix lost or misread evidence and prove local contract preservation, then compare alternative source organizations. Extract the numerical rule implementation separately with offline equivalence checks. Add new operators only for repeated valuable blocked designs, with declared semantics and a Consumer when execution is needed. Tune prices and performance only against a versioned reference world.

Archive successful and failed candidates with their provenance. Quality-diversity search becomes useful when measured behavior and a trustworthy evaluator exist. Before then, a small human-reviewed collection of different interpretations is sufficient. Never optimize a universal score assembled from DPS, price and number of effects and call it taste.

The experiment record should end with the next smallest action, its acceptance evidence and unresolved questions. [PIPELINE-EVALUATION.md](PIPELINE-EVALUATION.md) remains the record of observed results; [PIPELINE-APPROACHES.md](PIPELINE-APPROACHES.md) records route decisions. Update those only with what was actually inspected or executed.

## Evidence for the concept proof of concept

Keep the concept sheet readable and place research records beside it. Reuse the existing request/response recorder instead of adding a mandatory generation stage. Retain each raw completion before parsing or repair, including unsuccessful attempts; transport failures need an explicit missing-output record. A repository revision does not freeze a dirty working tree, so also retain effective file hashes or use a clean committed revision for the study.

This is a record template, not a claim that these are implemented API fields:

```text
Run / candidate / parent revision:
Generator revision and effective-file manifest:
Exact skill, assembled request/schema, source packet and resolved rules:
Requested/reported model, exposed settings and unknowns:
Attempt and raw-output locations, including failures:
Distinctive behavior and intended player decision:
Positive and negative scenario, marked predicted or executed:
Behavior before/after revision: preserved, clarified, changed, lost or unresolved:
Actual checks and scope, separately from model/human judgments:
Evaluator's concrete account of the interaction and any misunderstanding:
Acceptance decision, decision maker, context and reason:
Calls, tokens, known/unknown cost, elapsed time and human correction time:
Remaining uncertainty and evidence locations:
```

A predicted scenario states qualifying inputs, limits and a situation where the mechanic should not help. It does not establish observed gameplay. Later runtime evaluation must also use independently chosen scenarios and establish that its policy can legally and competently use the mechanic. Distinguish invalid definition, missing implementation, evaluator misunderstanding, inability to exploit the rule, no useful contribution in tested conditions, and useful behavior disliked by players.

A changed trigger, dependency, cadence, target rule, resource budget or cross-copy restriction is a design change even when the repair passes more checks. Record what a revision removes as well as what it fixes. A model double establishes data retention, not semantic equivalence. Pair deliberately defective designs with valid controls and report false positives as well as missed defects. Require a semantic reviewer to explain a concrete interaction before using its judgment about value.

## Freeze the study after the proof of concept

Compare direct full-skill generation, the same permitted design space with light structure, and bounded targeted repair. Keep sources, rules and total budget comparable, including repair calls. If the structured candidate becomes the repair condition's starting point, record the pairing rather than treating it as independent generation. Human-supplied interpretation measures preservation of assistance; automatic interpretation is a generation stage and must be labeled separately.

Freeze prompts, schemas, checks, source packets, rubric, model/settings and effective code. Keep development references apart from held-out references and use publishable original briefs as well as familiar-character development cases. Conceal producing labels for human comparison, randomize order and record reviewer familiarity and disagreement. Repeated outputs share character, rules and condition; upgrades are not independent experimental subjects.

Select a principal outcome before the main study. Report eligibility and failures across all scheduled attempts alongside preference among eligible concepts. Record timeouts, abandoned corrections and a capped unsuccessful correction outcome rather than treating failures as zero effort. Separate readability, strategic consequence and preference. Cost per accepted design includes every generation, review and repair attempt; with zero acceptances the ratio is undefined, and unknown charges prevent an exact ratio. Report human time separately.

Six references, two rulesets, three conditions and two runs would produce 72 concepts. This is an illustrative pilot workload, not a justified sample size. Use the pilot to estimate review burden, failures and disagreement before selecting the main study. A stronger model may remove the benefit of extra stages, so retest the simplest baseline too. Concept evidence can support claims about fidelity, constraints, preservation and revision effort; gameplay claims require a compatible Consumer and executed comparisons.
