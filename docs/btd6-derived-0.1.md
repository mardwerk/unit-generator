# BTD6-derived candidate 0.1

The opt-in `btd6-derived` Definition provides a separate versioned authoring contract, compiler and stationary contact probe. Classic remains the default. The contract is a candidate; the initial capture-backed subset does not qualify a replacement game engine.

The author writes a base combat model and three paths of five upgrades. Numeric changes can compose across paths without property ownership restrictions. The compiler applies path order then tier order, so purchase order does not change a build. Exact endpoint overrides handle combinations whose captured behavior differs from that composition. Imported subsets can require explicit captured endpoints and reject absent builds.

The compiler checks all 64 legal authored builds, ID uniqueness, references, numeric limits and available targeting modes. Each authored purchase must change a resolved model in at least one legal immediate tier transition. This catches no-op purchases but does not establish their usefulness in play. It counts costs separately from combat state. The probe executes first/last/close/strong selection, local or global reach, walls, camouflage, damage immunity tags, idealized pierce contacts, independent attack timing, direct activated hits, exclusive temporary attack replacements, activation rejection and cooldown persistence. Stun and slow effects declare their own immunity tags and durations. Repeated hits refresh each source effect; the strongest active reduction determines integrated control time. Every probe result states its assumptions.

The `btd6-derived.model/0.1` projection target is the model schema exported as `btd6ModelSchema` and stored in `packages/definitions/schemas/btd6-derived-model-0.1.json`. A model contains `displayRange`, `targeting`, `attacks` and `abilities`. Source schema version, target identifier, source hashes, mappings and gaps belong to the Corpus export sidecar. Consumers must check the target identifier before validating the model. A validated model alone carries no source-fidelity claim. `consumeBtd6ModelProjection` checks exact target and translator versions, legal endpoints, model validity and required provenance fields. It preserves declared gaps and explicitly reports that it has not rechecked the private source hashes.

The raw captured graphs and exact source mappings stay in Reference Corpus. Public tests use synthetic inputs. Ninja projections still omit movement, track collision, projectile travel and bloon layer behavior. Wizard's Phoenix is an explicit translation gap. Synthetic self-transformation tests establish only this contract's lifecycle, not Wizard parity.

Paragon creation remains a separate future extension. This version also does not execute summons, support, income, statuses beyond stun and slow, resources, nested forms, projectile trajectories, moving enemies or target health/layers. Adding an unsupported string records a gap; it does not make the omitted behavior executable. Generated Luffy must disclose stamina and Gear lifecycle adaptations when using this contract. Those are implementation gaps in this candidate, not restrictions imposed by BTD6 itself.

Use `createBtd6Fixture()` for an original Clockwork sentry example. It is not captured game data. `compileBtd6Build(unit, [5, 2, 0])` resolves a build; `probeBtd6Build(build, scenario)` exercises the bounded behavior. No live game or server is required.

The fresh main-menu snapshot ending in `9a488f4440e9253f` produced four accepted model projections and one gap-only Wizard record. A two-second probe against three fixed targets produced Ninja damage totals 8, 10 and 15 across 000, 100 and 200, and Sniper damage 4 from two shots. Each executable projection retained five declared gaps. These checks establish projection field arithmetic under the stated contact assumption, not live game parity.
