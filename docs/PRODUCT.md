# Unit Generator

Unit Generator is a planned standalone Tool for adapting requested characters into Tower Defense units. Authoring can begin with explicit game scope and a partial Game Definition, then propose missing mechanics. Generation and validation against those mechanics require sufficiently specified rules and applicable Profile values. Its Engine owns unit generation, source evidence, mechanic interpretation and scoped validation. Unsupported abilities must be reported; extending a game's mechanics requires an explicit Definition change.

The Tool provides an adjustable default Profile and returns inspectable content, evidence and findings. Its CLI has no hidden state between calls. The optional UnitLab uses the same Engine and retains local settings, work and generation history; earlier Results become explicit inputs when reused.

Units must satisfy their declared requirements. Scoped checks alone do not establish balance across a game or player appeal. Towerright or another caller supplies wider evaluation and feedback; Towerright also retains project context and can provide curated Profiles.

Engine, CLI and UnitLab remain in this repository. Implementation starts from scratch; supported mechanics and generation features still need scoping.

## Next scope

The first implementation candidate is one standalone character-authoring operation. It helps a caller turn evidence and partial game rules into a reviewable Unit design with explicit mechanic requirements.

- Input: character and source scope, supplied evidence or research permissions, relevant game rules and Profile values, confirmed choices, requested outcome and input Revisions. Missing rules remain visible.
- Output: a connected Unit candidate, supporting evidence, required mechanics, proposed Definition extensions and findings that identify affected behavior and the next correction or decision.
- Completion: preserve confirmed choices, check sufficiently specified constraints, and distinguish contradictions, missing specifications and unsupported capabilities. A useful authoring result can retain open details; those details cannot receive a successful mechanics check.

A self-contained example should supply a game's upgrade rules, an attack and a wall-perception upgrade. It should return a candidate satisfying the stated progression rules while reporting unspecified attack delivery through walls. A legal combination alone cannot approve that delivery. Keep example rules in caller-supplied inputs; public examples must require neither Towerright nor private documentation.

Record one corrected candidate and its review findings before fixing the CLI format or default Profile. Keep generation, retrieval, deterministic checks and human decisions separate enough to use different executors with the same inputs and expected outcomes. No specific AI model or Provider is required. Complete DSL execution, game-wide balancing, UnitLab and runtime implementation are outside this first candidate scope.

## Requirements from character design

Status: September 19, 2026. These candidate requirements come from the Luffy, Alucard, Tatsuya, Gojo, Rimuru and Goku design passes. They describe standalone value and evidence needs, not implemented operations, a fixed schema or a selected release scope.

Explicit inputs need the character identity, source work and any selected story period, source material or permission and limits for further research, and the available Definition and Profile with their Revisions. Coarse game scope suffices for exploration; missing progression or behavior rules limit the claims that can be checked. Include confirmed adaptation decisions, the intended role if already chosen, and relevant earlier Results when continuing work. Missing choices remain visible; a character name alone does not establish a version or a kit. A standalone caller must be able to provide this context without Towerright or private documents.

Supplied reference links are research entry points, not an exhaustive source boundary or automatic proof of their claims. Within the caller's research permissions, follow up on specific techniques, limits and story periods as needed. There is no fixed search count. Expose unresolved claims when evidence is unavailable rather than inventing their behavior or asking the user to establish canon.

Before validating progression, its explicit input must resolve the permitted branches or other upgrade structure, depth, shared unlocks, prerequisites and legal combinations. Exploratory arrangements remain provisional while these rules are missing. The Result should connect a researched ability repertoire to one recommended arrangement and, where useful, a small set of alternatives for user selection. Show which techniques are innate, assigned to upgrades, reserved or omitted, with reasons where the choice matters. Do not assume every source ability needs a slot or that all games use the same path model.

Assignment checks should preserve confirmed choices, respect supplied progression constraints and reveal the consequences of moving an ability between tiers or paths. An alternative must remain coherent across its legal builds, not merely fit each ability into an empty slot. The Result needs to identify changed roles, lost combinations and dependent mechanics without presenting untested balance as established quality.

The proposed Result contains sourced character findings, a coherent Unit candidate connecting role, basic attack, upgrades and abilities, and a clear separation of confirmed constraints, proposed adaptations and unresolved questions. It also exposes spatial requirements for a caller or Map Generator. Keep sources and their limits attached to the claims they support. An inaccessible source is a research gap, not verified evidence. Reusing a familiar character must not silently merge incompatible story stages or continuities.

An explicit preferred reference and fidelity direction must be retained when supplied. Validate its claims against their publication scope and stronger evidence where they conflict. Preference for a source does not confirm every derived game effect. Check whether a canonical ability's prerequisites exist in the supplied game: a counterattack to incoming damage cannot function unchanged when that actor has no HP and receives no ordinary enemy attacks. Return the missing prerequisite and proposed adaptations without silently adding a durability system.

Validation needs to distinguish an allowed mechanic, an allowed mechanic whose exact behavior is still unspecified, a conflict with the supplied rules, and a requested behavior outside the Tool's supported capabilities. Extending a Game Definition is a caller decision and does not automatically implement support in the Engine. Findings should identify the affected part, governing rule, evidence and required correction or decision. Missing behavior cannot receive a successful mechanics check.

A stretching-punch example motivates these distinctions. A name and range do not say whether the attack hits one enemy, follows a path, hits several enemies or ignores obstacles. A supplied Definition might allow ordinary collision rules but require a separate rule for an attached limb. The Result must expose that dependency. A technique that changes terrain cannot be approved through a Profile that merely tunes damage and range.

Proposed checks include preservation of confirmed decisions, legal upgrade and form combinations, separate availability and readiness, explicit attack delivery and target eligibility, and the scope of any detection or collision exception. Form visuals must not silently grant unpurchased upgrade benefits. Path counts, unlock currencies, shield behavior and cooldown sharing come from the supplied Definition or Profile, never from universal Manga Mayhem defaults.

The partial armor-bypass example adds a concrete validation need: an exception must identify which protection it bypasses and which still apply. Under the supplied example rules, a shield intercepts the whole combined hit even when part of its damage could otherwise bypass armor. Without a shield, that portion can reach health while armor remains. These are requested checks against that Definition, not universal combat rules or tests already implemented. Progression checks should also expose upgrades whose advertised technique depends on a later form unlock, distinguishing an immediate benefit from a conditional one.

A persistent form selector adds another distinction: configured variant, activation command and currently active effect. Where the Definition permits preselection, the candidate must state its scope, persistence and use on activation, without treating configuration as an activation or an immediate transformation. Validation should check that a valid activation uses the configured variant and still respects readiness and active-form restrictions. The Consumer owns the concrete controls; the Tool must preserve the required interaction semantics without requiring a particular UI widget or hidden runtime state.

Alucard's initial research adds a version-compatibility case: a later character state may give up an earlier source of abilities. A Result must not silently combine that later state with the earlier army simply because both belong to the same character. His confirmed game regeneration also tests preservation of continuous effects across all legal upgrade paths and during Stun. Keep continuous duration reduction distinct from triggered removal, and preserve the declared behavior on effects already active when the upgrade unlocks.

The caller may deliberately request paths spanning incompatible source periods, as in Alucard's before-and-after branches and Red Sea utility branch. Accept that explicit adaptation direction while retaining the source distinctions and reporting its consequences. Validate the resulting legal crosspaths and any ultimate combination against the supplied game rules. Do not reject an intentional blend merely for differing from one canonical snapshot, or treat its approval as permission for unsupported mechanics. Path themes, ability assignments and compatibility decisions remain separate evidence.

Red Sea's Tier-5 global attack adds a composite-ability check: attack scope, summoned actors and their operating areas can differ. An explicit map-wide attack does not grant global movement or unlimited summons. Keep an ordinary high-tier active ability distinct from a separate fusion mechanic even when the caller informally calls both an ultimate. Unspecified relationships between an attack and its accompanying summons must remain visible in the Result.

The anchored manifestation case distinguishes a placed source from an alternate attack origin. A candidate must declare the source of perception, valid origin selection, attack delivery and attribution of upgrades and disabling effects. Rendering multiple appearances must not silently create independent attackers or bypass source restrictions. Compare this explicitly with autonomous summons and with relocation, which have different actor and spatial rules.

Successful later evidence should show a fully supplied candidate satisfying its declared rules and an unsupported candidate producing an actionable finding. This first pass has established neither a complete successful kit nor executable checks. Game-wide balance, usefulness across maps, player appeal and Acceptance remain with the caller; the Engine must state the scope and limits of its own findings.

The initial Tatsuya case requires independently declared detection and attack-obstruction exceptions, together with their unlock and availability conditions. Through-wall perception alone must not authorize delivery through the same wall, or imply camo detection or unlimited range. Triggered restoration also needs scoped exceptions: permission to start and complete restoration under a disabling effect must not leak into ordinary attacks or unrelated abilities. Preserve supplied removable-effect exclusions when evaluating a cleanse. These remain proposed validation requirements, not implemented guarantees.

The confirmed persistent wall-access upgrade adds a preservation case: once unlocked, no temporary activation window or separate uptime cooldown may be invented. This does not remove ordinary attack disabling conditions. Validation must distinguish a permanently owned capability from permission to execute an attack at a particular moment.

A multi-target restoration capstone requires progression-scoped cardinality: retain the earlier single-target behavior and expand only at the declared upgrade. Preserve activation, chant, cooldown and effect-removal rules unless separately changed. The Result must expose missing target count, selection and support reach instead of inferring unlimited or map-wide support.

Crosspath validation must distinguish coexisting capabilities from inherited behavior. A legal build containing a wall-access upgrade and a targeted area attack proves both are unlocked, not that the area attack inherits that exception. Preserve the supplied tier assignment, expose missing per-technique scope, and evaluate representative legal combinations using the caller's progression rules.

Personal precision and range do not authorize allied detection. A candidate using qualitative benefits such as "reliable attacks" must expose the missing operational meaning before mechanics validation can succeed. Do not silently translate that phrase into guaranteed hits, protection bypass or immunity to perception impairments. The caller's confirmed direction can be preserved while the detailed mechanic remains unresolved.

Research must precede generated clarification questions about a referenced ability. From the supplied sources or authorized research, establish the canonical behavior, limits and period, then derive the closest candidate consistent with confirmed game decisions. Return consequential choices about ability selection, path assignment and adaptation, with evidence and progression constraints explaining the alternatives. Canon can support several valid assignments; choosing among them is part of the user's creative role. A factual gap instead produces a research finding and a provisional candidate. An inaccessible link plus user-supplied text must retain both the attribution and the access limitation; it is not independently verified source content.

The anti-magic case requires distinct effect stages: countering a pending enemy spell, suppressing future casts and removing an already applied effect are different behaviors. Similar source names must not collapse them into one mechanic. The Result should identify the required enemy-action model and eligible spell events before claiming that an existing cleanse or Stun mechanic supports countering. Formula memorization likewise does not automatically authorize runtime copying of arbitrary abilities.

Rimuru's proposed repertoire separates acquisition, storage, analysis, configuration and use. Explicit inputs need the permitted technique catalogue, acquisition conditions, progression gates and behavior when no compatible sample is available. Results should expose unsupported samples and reward dependencies, including repeated acquisition from regenerated enemies. Automatic selection among owned ordinary attacks must preserve any manual activation requirements. A source's evolving skill names or Ultimate Skill rank do not establish game unlocks or fusion behavior.

Goku's teleporting Kamehameha adds a compound action: prepare, move, fire and return. The candidate must distinguish actor movement from an alternate attack origin and state how disabling effects, failed destinations and completion affect that sequence. Missing transition rules remain findings before mechanics validation can succeed. Spatial checks need the destination and return requirements; another character's form controls or teleport rules are not implicit defaults.

Gojo's Infinity and Goku's Ultra Instinct motivate selective prevention of incoming impairments. Inputs must distinguish prevention before application from restoration afterward, identify eligible effects and declare availability. A defensive source ability in a game without actor HP does not imply universal immunity. These proposals need explicit Definition support before the Tool can validate them.

Source prerequisites must remain visible when arranging legal builds. A composite technique can require basic capabilities without requiring every specialization associated with them. Environmental prerequisites likewise need an explicit treatment: retained, deliberately adapted or still unresolved. Results should show affected build and map scenarios. Official articles about other games may support a technique's identity while their damage, resources and controls remain separate adaptations.
